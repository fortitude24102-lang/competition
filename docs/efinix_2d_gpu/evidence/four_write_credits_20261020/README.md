# 小图块四笔写在途与2194活动精灵验证（2026-10-20）

本轮只验证已有 GPU 小图块写通路从两笔到四笔在途的收益，不改 CPU 栅格算法/配置、时钟、场景、Alpha/Key、软件 ABI 或网口。选择保留显式四笔候选及两笔回退；没有推送 main、替换release或写 Flash。

## 依据与实现

上一轮 Key 阶段的 B 等待观察值约占窗口52%，但该计数与其他工作重叠，不表示有52%的可消除瓶颈。四笔是否优于两笔必须测量。

新增默认值为2的 `writeCredits`，只允许2/4；`--four-write-credits` 选择4，并要求原有 Key write pipeline。同步调整 AxiWritePipeline 的响应标记队列、DdrQosArbiter 的响应归属队列和 CachedKeyStream 的待完成行计数宽度（四笔时3位）。像素 FIFO16不变，没有新增 DMA/大块 RAM。仲裁器仍在选 AW 前预留空间、最后一个 W 后登记归属；错误不撤回已呈现 AW，也不放弃已承诺 W/B。

参照 [verilog-axi axi_fifo_wr](https://github.com/alexforencich/verilog-axi/blob/master/rtl/axi_fifo_wr.v) 按完整写数据条件控制地址放行的思路，保留本工程已有逐行数据信用。只借鉴方法，未导入第三方代码；四笔响应信用是本工程现有写通路的小范围参数实验，不主张其本身为新算法。

## 已验证的离线结果

测试先于生产修改：`red-r1.log` 明确因旧 AxiWritePipeline 不支持 writeCredits 而失败。四个相关套件26/26通过，加上真实 RenderEngine 四笔整链路用例1/1，共27项（`green-r1.log`，命令退出0）。

覆盖四笔同时在途/第五笔阻塞、四个 B 错误位置及错误 BID、跨4KiB拆分的请求级错误归属、四笔待完成行计数、Render/Asset 响应归属和反压、扫描输出紧急优先时已呈现 AW/W/B 排空；真实 Copy→Fill→偶数宽缓存Key→Alpha 的逐字节像素、半字/4KiB和6类读写故障及后继命令恢复。

固定 B 延迟的同一仿真操作序列为2511→1750周期（约−30.31%）。这是模拟延迟下的序列耗时，不是实际 DDR 或游戏 FPS；其中也包含后继 Fill/Key/Alpha，不标成单纯 Copy 内核耗时。保留默认两笔回归。遵照不重复长时间验证的要求，没有重跑整个 CPU/SoC 项目；此前两项 SoC 固件异常不在本轮宣称解决的范围。
