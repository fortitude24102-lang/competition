# V3 负责人第6～7天：物理双缓冲背景恢复

## 状态和取舍

正式模块、GPU接入口、黄金检查及JTAG对照已实现；这是候选验证，不是V3封版，也不是512 Sprite稳定60FPS。默认`V3_GPU_DAMAGE=0`，保持原硬件、完整背景正常固件及release/v2。主负责人后续第8天整机集成需要A/B独立模块，不擅自接管功能线。

CPU绘图算法、R7 seed=7/运动/Alpha比例、960×540 HDMI、官方Sapphire100MHz、GPU RTL和资源未变。优化的是GPU命令生成/调度，不是CPU对照算法。板测只写JTAG易失状态，未写Flash。

## 实现合同

- `sw/efinix_gpu/include/gpu_damage.h` / `src/gpu_damage.c`：输入背景Copy、当前原命令流、资源epoch和每个物理buffer历史；`gpu_damage_plan`输出非负恢复数量/Copy列表，负数表示错误。16/32tile、gap0/2/4、最多128矩形；容量超限或估算不划算时恢复完整ROI。
- 恢复的是目标物理buffer两帧前遗留的覆盖，不是最近显示帧。包含Alpha/透明边缘的整个旧包围盒；之后全部当前Sprite按原顺序执行一次，不重复Alpha。成功完成后才提交覆盖历史。
- HUD y<72不属于恢复ROI；CPU写显存、素材换代/地址变更、渲染/HUD/PRESENT失败和reset使两块历史失效。首两块冷buffer完整重建。旧资源未被改写前，调用方必须先失效；不能只在下载完后才更新epoch。
- `perf_render_gpu_damage`只作用于场景，HUD继续用原`perf_render_gpu`。中途提交/完成出错只失效并返回，不从头重放。
- `main.c`可用`V3_GPU_DAMAGE=1`启用候选；当前固定素材epoch=1，因为原R7没有运行时换素材。第8天整合B的资源epoch时必须接真实epoch/失效调用。CPU窗口仍完整背景，不使用此策略。
- state/result位于BSS，不占官方4KiB栈。历史由5400 B字节网格压为675 B位图；合并O(tile数+矩形数)，不依赖研究探针。

## 正确性和规划瓶颈

RED：完整背景旧控制在第二次同buffer绘制时搬898560 B，测试要求仅恢复旧16×16的512 B，按预期失败。GPU接入口的完整Copy控制也在恢复宽度16而非960的断言失败。

最终入口：`powershell -File scripts/test-v3-gpu.ps1 -SoftwareOnly`。八个C套件（含审查后严格验收检查）、UBSan通过，六种策略×五档×600帧=18000帧ROI逐字节相同；涵盖CPU污染buffer、epoch换背景、HUD保护、边界、容量/成本回退、失败不提交历史、提交中断不重放Alpha。原R7像素CRC、游戏状态、HUD和纯软件对照检查通过。

板上36帧（六策略×六帧）的449280个ROI像素全部与完整GPU重建一致。核对在首次PRESENT之前进行，避免CPU大规模DDR读取干扰扫描输出；不声称该实验解决CPU-DDR与显示并发压力。计时阶段不跑逐像素CPU核对。

首版策略虽减少GPU搬运，但规划本身耗时严重。独立Sapphire测量512档、100样本（无渲染，不能视为FPS）：
