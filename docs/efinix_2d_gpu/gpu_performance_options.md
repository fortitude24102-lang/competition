## 9 月 28 日执行与 GitHub 复核

本地已组合 A-work 最新画面与 main 的性能 RTL，并实施 GPU 模式 HUD
使用现有 Copy DMA。按用户要求，CPU 屏显保留，CPU 场景/HUD/编译与主频
维持新场景原基础实现，不新增优化或 GPU 卸载；撤回本轮共用的 HUD
按变化行更新试验，历史数据单独保留。没有引入第三方 RTL、改变官方
RISC-V 或更新 V2 发布包。后续 GPU 专属优化不得改动 CPU 对照路径，
同场景与同功能前提下提高 GPU 帧率，不人为降速 CPU。
实测与限制以 [本轮板测](bullet_board_bottleneck_20260928.md) 为准；
下方 9 月 27 日的 S1～S3/H1～H2 是原始建议；当前 H1 对齐子集已
进入实现/验证，不把尚未完成的板测当作收益。

针对 GPU 的下一项硬件改动优先 H1：在不改变透明像素语义的情况下，
将 Color Key 连续地址打包成带 WSTRB 的短突发。512 档 Key 约 8.7～9.3 ms，
而 Alpha 约 2.5 ms，不能只因某个开源 DMA 名气大就继续优化非首要部分。
Copy 增加本地读写解耦 FIFO/事务流水作为下一层候选，不先保证 FPS 倍数。

H1 当前实现复用 `DenseBlitEngine` 的 Copy 字直通：对齐、偶数宽度
Color Key 每拍比较两个 RGB565 像素并生成 WSTRB，全透明字保留
零 strobe beat，整行使用现有 AXI 引擎拆分；奇数宽度和错位仍使用
旧像素路径。没有新增外部 IP 或改变命令 ABI，也没有改 CPU 路径。
这种直接字路径不能解决所有错位短行，后续收益以固定档位实测为准。

已完成半字相位字 DMA 候选及板测，详见
[本轮实现/验证](key_phase_dma_20260928.md)。完全对齐仍直通；非重叠 Key
增加移位/携带和首尾 lane 掩码，CPU/画面/软件 ABI 不变。512 档 Key
较上一候选再降 6.5%～9.0%，但完整帧仍未稳定达到 60 FPS。
图集 BRAM 热点缓存随后已经实施并通过板测：4 KiB 软件管理 Cache 使
512 档 Key 再降至 2.621～2.796 ms、FULL 降至 12.304～12.365 ms，
但普通 64 档渲染只由约 10.22 ms 降到约 9.30 ms，屏显仍为
40.0～58.1 FPS。详见 [纹理 Cache 板测](texture_cache_20260928.md)。
因此 Cache 不再是“待实施建议”；下一首要候选改为双缓冲感知的背景
脏块恢复或静态背景分块，以减少每帧约 1 MiB 的全屏背景读写。

特别注意：当前 `DdrQosArbiter` 物理读通道一次只处理一个事务，写通道
等待 B 后才释放。即使接入支持多笔未完成请求的 CDMA，也不会自动得到
该吞吐；需要共同审查仲裁、响应缓存、完成标签、背压、错误与扫描水位。
不能删除现有整突发响应缓存换速度，它用于避免渲染背压阻塞显示。

以上为本项目适配判断，不是开源作者宣称 Ti60 能达到的性能。

## 先更新判断依据

main 已完成 Alpha 最多 64 像素分块读/写和对齐 Copy 的 32-bit 直通，
不能把这两项再次当作尚未实施的主要建议。旧 32 Sprite 画面中，Copy
约 22.0→8.2 ms，Alpha 约 53～62→4.0 ms，正常 GPU 对比约 20 FPS，
但 GPU_300 报告 242100 次显示下溢。因此优先级是显示安全，其次是
Color Key 碎片事务与背景恢复；不是先提高频率或扩大 Alpha 数量。
来源：[main 性能定位记录](https://github.com/fortitude24102-lang/competition/blob/9f2eaba/docs/efinix_2d_gpu/v2_bottleneck_analysis.md)。

当前新画面不是旧 64×80 Sprite 场景：子弹主要是 8×8，512 档完整可见
场景上限 585 条命令，最多 68 条 Alpha；同一 3104 字节图集反复使用。
实际瓶颈可能转为命令提交和短行事务。以上为结构分析，不是新场景板测。
迁入主负责人当前硬件后，要重新测 32/64/128/256/512 档位，不能套用
旧场景 FPS 或声称已经达 60 FPS。

## 二、针对当前设计的建设性方案

### P0：先解决显示下溢，并建立新场景基线

- 用相同逻辑 tick、相同素材和对象档位比较 CPU/GPU；分别测背景、
  Color Key、Alpha、HUD、PRESENT 与总帧时间。现在的 Profile 是 32
  目标对象短诊断，后续需扩展压力档位与持续运行，不能用短时零下溢
  代替长期验收。
- 捕获扫描 FIFO 最低水位、补充请求至第一 beat 的最大延迟、行缓冲
  就绪和 AXI AR/R/AW/W/B 进度；区分真实缺像素、启动/翻页时序问题
  与计数/跨时钟问题，不先断言 242100 是某个单一根因。
- 现有仲裁器已支持扫描紧急优先与 256-beat Render 响应缓冲，不能只
  说“加入扫描优先”。已授予的长 Render 突发不能中途抢占；考虑提高
  安全水位、提前 refill，及在不破坏 AXI 的前提下限制 Render 单次
  突发长度。大突发吞吐与扫描最大等待之间要受控权衡。
- 水位预算应覆盖“最大不可抢占时间×像素消耗速度＋CDC/请求余量”，
  不是盲目把 FIFO 加大。检查每行能否及时补充、持续供给是否不足。

验收：新场景持续渲染与翻页中下溢增量为零，画面无黑线/撕裂，随后才
看速度。仿真验证最坏 AXI 延迟、背压和帧边界；长期板测另做。

### P1：Color Key 由逐 beat 写变成带掩码的连续片段写

main 的动态 Color Key 写请求仍为单 beat，新的 8×8 子弹每行更短，
地址/响应开销容易超过像素计算。先在一行/短片段积累多个 32-bit 字，
使用 WSTRB 为非透明 RGB565 像素启用对应两个字节通道；全透明字可用
零 WSTRB 占位维持一次连续突发，或在透明区域处分段。比较两种策略
的事务数量和总字节量，不能假设“少写字节”必然更快。

保留奇数 x/宽度、行尾、4 KiB 边界及透明不覆盖背景语义，不把透明
键色写进去，也不重排相互重叠对象。验收：逐像素相等、授权次数/有效
像素下降、阶段耗时下降且显示无下溢。

### P1（已完成）：小图集驻片上缓存，重复命令复用源像素

本图集仅 3104 字节，现已使用 4 KiB、软件管理的 BRAM Cache 避免几百颗
子弹反复从 DDR 读取同一图集。初始化仍由 RISC-V 请求素材、验 CRC，
随后显式装载；图集更换/失败回退可失效。512 档 Key 的 DDR 前景读取
实测为 0，减少的 FULL DDR 读字节与 Cache 读字节逐项相等；Alpha 目标
背景读/写仍然存在，没有宣称消除全部 DDR 流量。代价为 4 个 RAM10，
普通 64 档整帧收益约 9%，说明该项完成后应转向背景 Copy。

### P1：静态背景采用合并的脏块恢复

无需新增 GPU 操作码即可先做软件试验：记录旧对象与新对象、Alpha
光晕和 HUD 变化的覆盖区域，按 16×16 或 32×32 格合并，再从不可变
背景恢复对应区域并重画所有相交对象。密集/大范围脏区时回退全屏 Copy，
阈值由计数和实测决定，不预先许诺性能倍数。

双缓冲要分别记录各缓冲上一次实际呈现的状态：当前 back 可能存的是
两帧以前的图。不能只擦“上一帧”，也不能在没恢复背景的像素上重复
叠加 Alpha。重画顺序、粒子出生/死亡、护盾和 HUD 都须纳入。

### P2：减少每个小 Sprite 的 CPU/APB 提交开销

现有驱动已用 16 深度批量队列，单纯再称“做批处理”不够。下一步可
缓存连续相同的命令寄存字段，只更新变化的坐标，或引入 DDR 描述符
列表/instanced blit：一次提交共享图集、尺寸、颜色键和坐标数组。
后者需要 GPU 命令 ABI 升级，应保留旧驱动兼容并单独验证。

记录命令提交 CPU 周期、队列空闲时间和像素引擎空等；只有确认 APB
供给不足才实施。512 个小对象不能被几百次软件轮询拖成低利用率。

### P2：片段双缓冲与有限未完成事务

main Alpha 已有前景/背景配对缓冲，但读取、混合和写回的片段阶段仍
值得评估 ping-pong 重叠；Copy/写引擎还会等响应。参考 DMA 的结构，
先做“下一片段预取与当前片段处理”而不是马上放开无限 outstanding。
再评估多笔未完成读/写，需一起处理 AXI ID、返回顺序、4 KiB 边界、
错误粘滞、跨命令完成边界与 DDR 仲裁，不能只改一个状态机参数。

### P3：局部目标块缓存或扫描线合成

对多对象重叠区域，先把背景 tile 读进片内 RAM，按原顺序处理 Color
Key/Alpha，最后整块写回。16×16 RGB565 tile 为 512 字节；ping-pong
两块为 1024 字节，不含标签/源缓冲。它减少的是重复背景 RMW，不是
整个 1MB 帧缓冲都能塞入 BRAM。代价是按块分桶/边界裁剪和一致性。
直接扫描线合成可进一步省去整帧恢复，但改变显示架构、时限及基准
口径，作为较远方案，不是这次入口替换的一部分。

S1～S3 仍是工作量/结构估算，不是已测 FPS 或性能倍数。H1/H2 已完成
独立板测，不应再次列为待办。后续先验证背景脏块恢复，再考虑描述符
列表、片段重叠和目标块缓存。

#### S1：消除被 HUD 覆盖的背景搬运

位置：`sw/efinix_gpu/src/bullet_demo.c` 的 `bullet_build_frame` 背景
命令，以及 `main.c` 的正常 HUD 路径。现在背景复制 960×540，随后
`hud_cached_command` 又完整覆盖 960×72，正常最终画面中前 72 行背景
数据不会保留。

正常 HUD 路径可把背景起始源/目标地址均加 `72*GPU_FRAME_STRIDE`，
高度改为 468，宽度与步长不变。每帧减少 138240 字节读和同量写；
按 60 帧/秒估算少约 16.6 MB/s 的背景流量，不代表达到 60 FPS。

边界：必须由调用路径明确保证 HUD 每帧完整覆盖。当前 Profile 不绘制
正常 HUD，不能无条件修改共享 builder，使诊断留下未初始化的顶部；
需保留完整背景策略或另行初始化该区域，并保持诊断口径明确。
测试不能只比较 HUD 前的场景，而要比较相同 HUD 输入下的完整最终帧。

#### S2：保留图案，只裁去恒透明外围

位置：`bullet_demo.c` 的 `bullet_shape_opaque`、`sprite` 与子弹命令
构建。下表由当前 8×8 掩码逐点枚举得到，偏移以原图块左上角为原点：

| 图形 | 有效区域起点 | 绘制尺寸 | 原处理像素 → 新处理像素 |
| --- | --- | --- | --- |
| 圆弹 | (1,1) | 6×6 | 64 → 36 |
| 空心环 | (1,1) | 6×6 | 64 → 36 |
| 针弹 | (2,0) | 4×8 | 64 → 32 |

其他三种仍使用 8×8。源地址增加对应 texel 偏移，源步长仍为原图块
的 16 字节，目标坐标增加同样偏移，然后对新矩形重新裁剪；不能把
图集重新解释为紧凑的 6×6/4×8 数据。游戏坐标、8×8 碰撞掩码和素材
CRC 都不变，不靠隐藏子弹减少工作量。近屏幕边界与 HUD 分界处的
实际可见数也必须不变。

验收：六种图形、各档位、四侧边界及奇偶 x 的最终像素逐点一致。
量化的是矩形处理像素，AXI 对齐可能增加首尾 beat，DDR/FPS 收益另测。

#### S3：驱动维护命令寄存器影子

位置：`sw/efinix_gpu/src/gpu.c` 的 `write_command`，必要时给
`gpu_device` 增加软件影子状态；不改变硬件寄存器或操作码。当前每条
命令重写 OP、SRC、DST、SIZE、两个 STRIDE、COLOR_KEY、ALPHA_FLAGS、
TAG 和 CONTROL 共约 10 个字段。

连续同规格子弹只写变化的字段；通常保留源地址、目标地址、TAG 和
CONTROL，裁剪或形状/效果改变时补写相应字段。不要为凑同类批次重排
对象，Alpha/重叠顺序保持原样。首次提交、初始化和硬件复位后全量写；
单一驱动独占硬件的条件必须成立。每条 TAG/提交及原有同步屏障、
错误检查、队列满处理都保留，不把缓存命中当作命令已经完成。

验收：驱动测试覆盖首次全量、连续相同字段、裁剪尺寸变化、KEY/ALPHA
切换、复位失效、错误/队列满与标签回绕；检查提交给硬件的完整命令
不变。记录实际 APB 写次数和提交 CPU 周期，确认像素引擎是否因此少空等。

#### H1/H2：针对短行与小图集，而非继续增大 Alpha 分块

H1 的具体位置是 main 的 `DenseBlitEngine.scala` 动态 Color Key
写请求及 `PixelWritePacker`/写缓冲：先收集一行的连续地址、数据和
WSTRB，掩码保护透明 RGB565 像素。8 像素对齐行是 4 个 32-bit 字，
可用一次突发发送；错位行可能需要 5 个字。透明字占位还是分段，由
实际事务/字节量选择。保留奇数宽度、4 KiB 边界和错误传播测试。

H2 在素材加载、CRC 成功或生成本地回退后填充源图集缓存；切换素材、
复位及重新加载时正确失效。小图集节约的主要是事务延迟，不应把几十
KiB 级重复源读取夸大成全屏背景级带宽瓶颈。用命中率、源 AR 次数、
阶段耗时及资源占用决定是否值得引入。

当前 Alpha 光晕宽度为 12，而 main 的分块上限已经是 64；单纯将上限
调为 128 对这些光晕不起作用。需要观察短行启动/背景读写与片段重叠，
不是再扩大一个用不到的参数。

#### 共用验收与停止条件

每项先建立能在修改前暴露问题的针对性测试，再单独实施；完整回归
一次即可，失败时只补针对性检查，避免反复重跑。S1/S2 比较相同状态、
相同 HUD 字段的完整帧，S3 比较真实命令与寄存器副作用，H1/H2 增加
AXI 背压/边界仿真。只有最终像素一致、对象/游戏机制不变且显示稳定，
才接受性能收益。板测固定逻辑 tick、档位、网络状态及 CPU/GPU 口径，
分别记录总帧时间、分阶段时间、读写字节、授权次数和下溢增量。
不得因提高 FPS 而接受新增下溢，也不使用旧场景 20 FPS 作为新画面结论。

### 完整帧流量预算

纯理论流量下界（十进制 MB，忽略 Sprite、缓存开销和对齐损耗）：
960×540×2 = 1036800 字节。若游戏与扫描均为 60 帧/秒，全屏背景读＋
写约 124.4 MB/s，扫描再读约 62.2 MB/s，合计约 186.6 MB/s；当前
960×72 HUD 全量 CPU COPY 另有约 16.6 MB/s。DDR 必须有额外余量支持
Sprite/Alpha 和争用；这些是工作量估算，不是已测 DDR 峰值。

近期顺序以 S1～S3/H1～H2 清单为准；长期再推进脏块恢复、描述符提交、
片段重叠和局部目标缓存。软件试验与硬件方案
分别成独立变更，保持同场景、同状态、同像素正确性和含 HUD/PRESENT
的真实帧率口径。不要先靠减少对象、关掉 Alpha 或降低分辨率来宣称
达标；这些只能作为明确标注的瓶颈对照，不是同等效果的加速。
