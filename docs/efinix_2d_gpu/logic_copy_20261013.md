# GPU调度重叠与封存预算：实测收尾（2026-10-13）

基线`ea434b6`，负责人在当前独立工作区连续实施。源实现`7e75e75`，采集身份修复`c867640`，末帧原始状态/回归入口`c893d7d`。本轮是有净收益的显式候选，不是V3全部完成或稳定512@60认证。无Flash、位流生成、release覆盖或远端推送。

## 保持不变与做出的改动

官方Sapphire、GPU100MHz、960×540 RGB565、原硬件Copy/Key/Alpha、DDR3和以太网保持不变；CPU基础绘图及游戏更新算法不改。沿用上一轮已加载的合格`frame_list_20261012_r1` BIT，文件SHA仍为`de8487d790dbac78e901816ed4dd46fd7cfb987b1b5e71724ff03d2aa072efea`，不是本轮读回芯片计算的哈希。台架COM9/115200，JTAG ID10660A79，PC192.168.1.2/板192.168.1.3；既有资源/网页服务复用。

- 最坏帧：终止DetailProbe存下实际最大work帧，记录排他的logic/build/scene/HUD/other，以及重叠busy、逻辑步数、HP/死亡等待/回合与seal_event；采样结束才输出，不再依赖30ms门槛碰巧遇到峰值。诊断成绩单独列，不混入常规成绩。
- 提前Copy：处理网口游戏命令后、游戏推进前，发原不可变背景到背缓冲，与RISC-V逻辑/列表构建重叠。逻辑推进能进入MENU/CPU，必须等原tag排空后才允许相应绘图；正常GPU复用tag、列表跳过已执行背景，不重复Copy。错误不PRESENT、不重放半帧；WIN仍走原硬件Fill。
- 封存预算：初始快照＋600输入满后保持不变，每次LIVE显示迭代最多扫描256个规范字，继续原游戏物理更新，不再记录第601个输入。512为5228字、21次迭代；256为2924字、12次。只有完整扫描后才sealed；原同步seal和`replay_begin`全量CRC校验保留。游玩中的Compare可多等约350ms（60Hz条件），但两后端仍回放同600tick；CPU绘图没有加速或参数改动。

复用原64B nibble CRC，不添加库，不减少任何规范字段。参考[zlib运行CRC分块累积说明](https://zlib.net/manual.html)，结合现有GPU帧预算做有界维护；不是复制其API的补码状态。独立逐bit规范序列参考在板上结果中给出256 `39ada006`、512 `c0ecf1df`，关闭/开启组相同。新游玩/重启/epoch/菜单/回放恢复均重置私有扫描游标。
