# 512 档：真实互动路径瓶颈复测（2026-10-11）

## 结论与边界

原合格四档菜单固件的终止式512诊断入口，30帧预热＋300帧采样：**30.0 FPS，帧工作均值19.602 ms，300帧全部超过16.667 ms预算**。实际可见497～504，Alpha命令66～67。新增下溢/硬件错误0，不能称512@60或30分钟耐久合格。

已定位两类不同问题：

1. 持续问题：游戏更新→GPU命令构建→场景提交/执行→HUD是串行帧关键路径。原固件真实遥测的构建约3.17 ms，场景约12.8～13.1 ms；HUD和游戏逻辑再占预算。即使低逻辑开销的普通帧也约17.6～17.9 ms。仅消除偶发尖峰不够。
2. 偶发问题：记录满600个逻辑tick时同步执行`replay_seal`，逻辑耗时约24.7 ms，整帧约42.8 ms。诊断直接记录`seal_event=1`，不是猜测网口超时。它是回放完整性校验，不是GPU像素运算；本轮只定位，没有修改校验或CPU绘图。

背景Copy隔离诊断约7.262 ms，是主要搬运热点，但该诊断改变了流水和代码布局，**不是原固件精确背景均值，也不是可与其他组直接相减的加速比**。精确的原路径“提交非阻塞开销/提交阻塞/执行尾部”尚未单独测定；本轮不把这一步说成已完成，不把busy当作纯硬件计算时间。

下一项优先验证：**先排入背景Copy，再在其执行期间构建Sprite命令**，让现有硬件搬运与Sapphire的GPU命令准备重叠；暂不优先加新CDMA、大Cache或乘法器。收益尚是预测，不能承诺512@60。校验尖峰也必须另外消除/分摊并保持回放校验语义，才可能谈长期稳定60。

最小DETAIL仅在终止诊断中启用：加两项时间戳、每30帧输出最后一帧分段值、发生>30 ms帧时输出seal事件。r1构建约3.09～3.22 ms，r2约3.25～3.39 ms；两组场景约12.79～13.07 ms，HUD约0.84～1.61 ms，普通逻辑约0.42～2.91 ms。上述范围包含预热窗口，**不是各分段300帧均值**。`hud_us`包括缓存变化处理、HUD Copy及其同步；`scene_us`包括CPU提交、阻塞、最后tag等待和后置同步。

DETAIL的`log_mean_us/log_max_us`只统计每30帧的窗口输出，不统计额外`V3_SPIKE`输出；尖峰输出时间仍计入下一帧work/wall，不会从总帧时间中消失。因此这两项日志字段不能当作DETAIL全部UART开销，独立审查将完整日志分项统计列为后续小项。`logic_us=24723`也是整个逻辑段（包括该帧游戏更新和seal），不是单独CRC函数的精确耗时。

两个运行分支的例子（r2）：

- tick178：逻辑420＋构建3254＋场景12968＋HUD932＝17574 µs，work17779 µs，剩余205 µs是快照/同步/控制/收尾等。逻辑较低的帧仍超过预算。
- tick418：逻辑2903＋构建3369＋场景12848＋HUD1475＝20595 µs，work20808 µs。30 FPS时游戏通常每帧追赶两个60 Hz逻辑步，这又增加工作量，不能把它误归于GPU。
- tick601：`logic_us=24723,work_us=42788,seal_event=1`；tick0启动帧也有>30 ms，但`seal_event=0`，并未计入300采样结果。

## 为什么弃用第一种探针的绝对CPU时间

新增`test_board_live_phases.c`复用真实V3源码，通过函数包装记录互斥阶段，并以OTHER承接未计时收尾；统计检查覆盖重叠拒绝、残差、最坏帧归属、预算及容量。它可以帮助定位大致热点，但不是布局不变的测量。

包装探针512测出构建7.982 ms、工作22.757 ms；不计时控制组工作22.726 ms，二者仅差31 µs。**这不能证明探针与原固件等价**：包装组256降至58.7 FPS，原256此前60.1 FPS；原512实际构建仅约3.17 ms。启用/禁用计时的固件仍各自编译，不是运行时同一二进制AB。

官方配置是4 KiB、1路指令Cache。热函数长度相同而地址改变，与代码布局敏感现象相符；没有独立I-cache miss计数证据，不能断言已证明具体冲突。最小DETAIL保留了下列函数原地址/长度：`gpu_submit 0x23b0/0x2dc`、`hud_update_gpu_cache 0x4178/0x3e4`、`step 0x56a8/0x54c`、`build_frame 0x5eac/0x4e8`、`game_build 0x7ca8/4`；V3入口仍`0x8f98`，仅入口函数增长。循环本身布局及日志仍有扰动，所以以原组遥测为准，DETAIL用于分段及事件归因。

## 背景搬运与下一步架构选择

隔离组保持原命令顺序和Sprite，但先提交背景1条并等待完成，再提交其余Sprite，从而主动打断原CPU/GPU流水：背景7262 µs，其余3836 µs，场景11106 µs，work22874 µs。它与历史背景隔离约6.94～7.61 ms数量级一致，不用于证明原场景各占比或新调度收益。

源代码证明每帧背景是960×468 RGB565，**读898560 B、写898560 B**；HUD960×72，读/写各138240 B。已避免复制被HUD覆盖的72行背景。3104 B弹幕图集已进入纹理Cache，继续增加小图Cache不会消除上述背景流量。

优先试验现有Copy与GPU命令构建重叠，而不是直接替换硬件：

1. 在上帧PRESENT完成、确定backbuffer后，先构建并提交同一个468行背景命令。
2. Sapphire继续生成/裁剪相同Sprite指令；背景在此期间搬运。保留全部地址/尺寸校验、tag及超时处理。
3. 从第二条起按原顺序提交，背景必须先于任何读改写Alpha；全部Sprite和HUD结束后才能PRESENT。资源变更、CPU比较、菜单及错误回退保持原路径。
4. 做字段/顺序/最终像素等价检查，再同一原入口旧→新→旧实测；检验新增Cache同步/代码布局扰动是否抵消重叠。不减少像素、对象或Alpha，不优化CPU比较。

最多可隐藏的构建时间约3.2 ms是**上界预测**；DDR竞争、提交和逻辑分支仍可能使实际收益更小。CRC尖峰仍在，不能以平均工作<16.67 ms代替稳定60验收。

精确提交阻塞仍待单独确认：旧`submit_probe.h`启用后反复调用`gpu_try_submit`，重试会重复校验，不等于当前默认validate-once路径。不能把历史probe的提交数字当作当前512原路径；下轮需用语义一致的最小探针，并同时给出未插桩控制，区分APB写入、信用轮询和硬件尾部。
