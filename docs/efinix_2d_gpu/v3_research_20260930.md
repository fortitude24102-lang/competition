# V2 收尾后的一个月：设计革新与功能创新调研

日期：2026-09-30。分析基点 85b7dc0；当前硬件为 9/28 纹理 Cache 候选。
本报告是调研、研究专用主机校验和候选决策材料，**不是已批准实施计划或新版本成绩**。本轮未改生产固件/RTL、未引入第三方 IP、未烧录、未更新 release。按用户给出的“剩余一个月”安排 30 天，不推断官方截止日期。

## 1. 目标和不可改变的边界

目标不是多加几个外设，而是形成一个“能互动、稳定显示、性能提升可解释、第三方可复现”的 RISC-V + FPGA 二维渲染作品。

- 保留官方 Sapphire CPU 与 DDR3/HDMI/GE 基础；RISC-V 决定资源、输入、移动、碰撞与 GPU 命令。
- PC 网络服务只提供资源。若临时用 PC 键盘作为输入设备，也只发按键状态，不发坐标/轨迹/碰撞或渲染结果；若严格要求 PC 连输入转发都不做，采用板键/外接手柄。
- CPU 绘制对照保持基础实现，不新增 CPU 专属优化、不 GPU 卸载、不人为降速。GPU 命令前端卸载不等于优化纯 CPU 绘制。
- 不减少 Alpha、Key、同屏对象、分辨率或显示扫描，不用撕裂/下溢换 FPS。
- “创新”指本工程可验证的针对性组合，不把 Burst/FIFO/DMA/Cache/脏块称为首创，不声称全球首次。
- 前两周最多选择一项较大架构修改；最后至少五天只验收、冻结和准备证据。

## 2. 充分理解当前设计后，真正的优化空间

从 main → bullet_build_frame → gpu_submit → APB 队列 → DenseBlit → AXI → DDR/QoS → Scanout/PRESENT 检查了实际路径。

| 已有能力 | 当前限制 | 不能重复包装的建议 |
|---|---|---|
| Copy 对齐时直接 32-bit 搬运，R→W 已逐 beat 流式重叠，不经过 Alpha 乘法 | 数据源受写端背压耦合；每行等待源读和写响应结束再进入下一行 | “首次绕过乘法/首次读写重叠”均不成立 |
| 最长 256 beat INCR、4 KiB 切分 | 一笔读事务完成再发下一 AR；每 burst 等 B 再发 AW | 只调大 Burst 不足以解除事务串行 |
| 256 项渲染 R 响应 FIFO、显示水位迟滞与防饿死 | 仲裁只有一个物理读 owner，新的 render AR 要等响应 FIFO 空 | 加多 ID 的 CDMA 不会自动得到多在途能力 |
| 4 KiB 软件显式纹理 Cache，图集 3104 B | 缓存小 Sprite 的前景，不缓存完整背景和 Alpha 目的像素 | 扩大现有图集 Cache 不触及最主要流量 |
| 最多 16 条在途，批量提交，批尾等待一次 | 每条仍反复校验/读状态及写约 10 个 APB 寄存器 | “去掉每命令 wait”已经做过，不能重复计收益 |
| GPU HUD 仅更新变化字形 | 每帧仍整条 Copy 960×72 HUD | 单数字更新很小，文字专用 DMA 不是第一优先 |
| 同状态 CPU/GPU 交替、R7 自动生存 | 无玩家操控，按键管脚与软件提示不匹配 | 仅添加更多自动动画不能补“互动游戏”要求 |

关键源码：DenseBlitEngine.scala、AxiReadEngine.scala、AxiWriteEngine.scala、
DdrQosArbiter.scala、gpu.c、perf_demo.c、bullet_demo.c、hud_gpu_cache.c。
路径根分别为 chisel/src/main/scala/gpu/ 和 sw/efinix_gpu/src/。

[9/30 实测](render_phases_20260930.md)的 512 档：PRESENT 前平均 19.263 ms、最大 20.855 ms，60 Hz 预算缺口约 2.60/4.19 ms；构建 3.101 ms，场景 13.436 ms，硬件 busy 12.028 ms。提交压力、busy、场景时间互相重叠，不能相加。隔离背景约 7.6 ms，读/写各 898,560 B，占场景 DDR 读约 97.7%、写约 94.5%。

当前 32-bit、100 MHz 数据通道每个方向理想上限 400 MB/s：上述背景单向最低 2.2464 ms；如果读写完全串行，数据本身至少 4.4928 ms；完美重叠才可能接近 2.2464 ms，还未计 DDR/显示争用和响应。完全串行是对照下界情形，**不是当前架构描述：现有 Copy 已逐 beat 同时读写**。若只靠背景缩时弥补预算，平均要求其约降到 5.0 ms、最大约 3.4 ms。这不是预测：需要提高现有重叠的有效占用率、跨事务流水，或组合流量消除/前端减负。

## 4. 本轮实际初步校验：脏区域不是“肯定更快”

研究工具 [probe_damage_tiles.c](../../tools/probe_damage_tiles.c) 直接编译当前
bullet_demo.c、golden_renderer.c、rgb565.c，读取正式 R7 背景和图集。
不是另写一个猜测弹幕分布的模型。

- seed=7，五档 32/64/128/256/512，每档 600 tick，保留所有 Alpha/Key 原顺序和裁剪。
- A/B 各记自己的旧 Sprite/光晕覆盖。恢复该 back buffer 旧覆盖，再把**全部当前 Sprite 按原顺序绘制一次**，避免 Alpha 累积和跨缓冲残影。
- 16/32/64 三种 tile；水平间隙允许 0/2/4 个 tile 合并，垂直仅合并相同 x 范围。
- 每种方案两块缓冲初始化；tick300 模拟 CPU 覆盖后使两块历史失效；tick450 模拟背景改变并失效。每组共六次全恢复。
- 对每帧 y≥72 的完整 ROI 逐字节比较，不是只比较覆盖或 CRC。45 组、共 **27,000 帧**全部相等，UBSan 未报告错误；HUD 不在比较范围，现有 HUD 测试另有证据。
- 两个故障注入：误用另一块缓冲历史、CPU 覆盖后不 invalidate，均触发像素不等断言。证明这些保护不能省掉。
- 数据是主机像素/几何结果，**不是 Chisel 新架构仿真、FPGA 时序结果或板上加速/FPS**。未重跑全项目/长 RTL 回归，历史两项 SoC 异常仍保留。

512 档稳态结果（排除六次全恢复；burst 是模拟现有逐行 256 beat/4 KiB 拆分，**每方向**，不是板上新增计数）：

| Tile / 水平合并空隙 | 背景恢复面积平均/最大 | 恢复矩形平均/最大 | 读 burst 平均 | 相对原全背景 |
|---|---|---|---:|---|
| 原全背景 | 100%/100% | 1/1 | 1112 | 对照 |
| 16 / 0 | 27.924%/31.895% | 152.61/186 | 3011.51 | 少字节，但 burst 是 2.71 倍 |
| 16 / 2 | 33.672%/39.715% | 104.65/138 | 1965.41 | 仍碎片较多 |
| 16 / 4 | 42.029%/52.137% | 71.50/104 | 1354.87 | 面积下降与事务增加之间折中 |
| 32 / 0 | 49.018%/56.353% | 60.89/82 | 2159.84 | 仅少字节不足以保证收益 |
| 32 / 4 | 66.542%/80.285% | 18.43/28 | 1006.40 | 少约 33.5% 字节，突发略少 |
| 64 / 4 | 82.763%/96.125% | 6.67/9 | 1012.53 | 省流量有限，管理简单 |

16/0 的稳态读写合计约 0.502 MB，32/4 约 1.196 MB，原背景约 1.797 MB。
这些只计算背景恢复，不包括仍然完整绘制的 Sprite、HUD、扫描或描述符。
间隙合并故意多恢复部分背景，以换更少短事务，像素比较已验证其不改变结果。

**修正原先直觉：**当前逐行 DMA 下，“16×16 脏块 + 一个 Copy/矩形”可能比整背景更慢。值得创新的是用实际字节、burst 和命令开销共同选择恢复粒度，而不是只最小化像素面积。

32/4 为一项可先板测的折中候选，不是已选定最优参数。若总耗时完全按字节比例缩放，其平均背景约可省 2.54 ms；仅是乐观估算，几乎刚好等于平均预算差，没有覆盖最大帧、额外命令和失效恢复。不能据此保证 512@60。
连续 GPU 每组只有六次失效恢复；正常 30 帧 CPU/GPU 交替会更频繁失效，必须独立测，不用本组稳态覆盖率代替它。

## 5. 四项值得考虑的性能设计革新

### P1：连续 Copy + 读写解耦的受限流水

**推荐先做，通用硬件收益最直接。**现有 APB/Copy 命令不变，源/目标均对齐、
src_stride=dst_stride=width×2 且非重叠时，把矩形展开为一个连续字节任务；
非连续/错位走旧通路。HUD Copy 同样可用。

逐行背景理论为每方向 1112 个 burst，连续描述可降为 878，少约 21%；
这已按当前地址与 4 KiB/256 beat 计算，数据量不变。单独删行间几拍通常
不够省数毫秒，不能把 21% burst 降幅写成 21% 时间收益。

现有 R→W 已逐 beat 流式重叠；随后评估有明确信用额度的小数据缓冲，隔离写端
背压/地址等待，允许后续 burst/行准备与前一事务响应阶段流水，正确聚合 B
响应后再完成 tag。目标不是首次重叠，而是减少既有重叠被串行边界打断。
复用现有缓冲、切分和 QoS；不要无条件同时发整个背景的
全部请求。更大在途窗口需一起修改实际仲裁 owner/RID 路由与容量预留。
参考 CDMA 的传输结构而非复制后接上线就宣布完成。[源代码](https://github.com/alexforencich/verilog-axi/blob/master/rtl/axi_cdma.v)

创新候选：**显示余量约束的连续二维搬运**——显示低水位时限制新请求，
已承诺返回数据有容量保障；跨事务流水但 Copy 和后续重叠 Sprite 仍按命令顺序。

最小校验：连续/非连续/4 KiB/尾字节/反压、随机 AXI 延迟、B 错误、完成顺序、
PRESENT 前所有写响应完成；记录 AR→首 R、RLAST、WLAST→B、FIFO峰值、
最低显示水位。普通固件同场景复测。先用波形测实际事务空洞，不重测已知大阶段。
连续子集约 3–5 天；包含受限流水/仲裁修改约 10–15 天，工期不是叠加承诺。

### P2：双缓冲感知的自适应背景恢复调度器

不是“只画移动物体”，而是**恢复旧覆盖，全部 Sprite 重画一次**。
保留 Alpha/Key工作量、顺序与最后图像；因此不会靠跳掉透明混合提高成绩。

16×16 网格元数据每块 1800 bit=225 B，两块仅450 B；研究探针用字节数组是
为便于检查，不是最终硬件面积。实际实现还需有效标志、资源 epoch 和临时区。
恢复大小可在 16/32 tile、水平合并、全背景三种策略中选择：

    估计代价 = 搬运字节项 + 短 burst 项 + 描述符/提交项

系数从当前板卡同入口测出，不凭“面积最小”固定参数。
资源换代、CPU窗口、异常恢复、复位导致两块历史失效时先完整重建。

创新候选：**双缓冲 epoch + 碎片感知的恢复选择**；不是发明脏矩形。
开源区域合并和 buffer-age 的核心概念可借鉴，但本场景需单独保存所有旧
Alpha光晕，并正确处理 CPU/GPU 窗口切换。[LVGL](https://github.com/lvgl/lvgl/blob/master/src/core/lv_refr.c)、[KHR partial update](https://registry.khronos.org/EGL/extensions/KHR/EGL_KHR_partial_update.txt)

可先用现有 Copy 做 GPU 专属原型，不改 CPU 对照。若71/152条小恢复命令
吃掉收益，就改为恢复列表批量展开，或选32/4全背景回退。P1/P2能组合，
但互相收益不能直接相加。约 7–12 天；像素方案已初步校验，板端净收益尚未知。

### P3：模板状态 + 有序紧凑 Sprite 实例前端

GPU侧保存图集基址、stride、尺寸、Key等模板；RISC-V仍计算位置、动画、
Alpha、裁剪及顺序，只提交变化实例。硬件展开至现有验证器/命令后端。
保留老 APB 全字段接口作为通用/诊断回退，新增接口合同应先冻结，再让软件
与 Chisel 使用独立向量并行开发，不让团队互等实现。

以假设16 B实例为预算模型，约581个Sprite仅9.3 KiB/帧；目前约582条命令
需要约5820次寄存器写。新实例不是已定 ABI，不能把这组字节预算当成性能实测。
目标针对3.101 ms构建和提交里的非阻塞工作，不承诺消掉8.441 ms队列压力：
等待GPU消费的时间不会因换格式自动消失。

参考批量 DMA、维度展开、有序流。[Endeavour2](https://github.com/petrmikheev/endeavour2/blob/master/rtl/src/main/scala/endeavour2/DmaController.scala)、[iDMA](https://github.com/pulp-platform/iDMA)、[OpenGlory](https://github.com/egorxe/openglory)

创新候选：**适配小 Sprite 和纹理 Cache 的有序实例命令**，在CPU保留玩法的
同时降低每个对象的描述成本。不能按操作全局重排Alpha，也不能让PC生成实例。
校验展开命令与旧流逐字段等价、剪裁/模板越界、错误停机、tag/IRQ顺序；
若DDR描述符DMA新增争用，可先评估APB顺序流写入。约10–15天，中风险。

### P4：片上目的 Tile 合成，Alpha不再逐次往返DDR

在小Tile内读背景一次，将相交的Sprite按原绘制顺序全部混合/Key，最后
回写一次。不是扩大前景纹理 Cache，而是**目的像素工作集缓存**。
16×16 RGB565为512 B、双Tile为1 KiB，另需源读缓存/索引/端口和控制；
32×32单Tile为2 KiB。

若仍处理全屏全部Tile，背景读写量不变，单靠Tile本地Alpha不会解决97.7%
背景读流量；需要配合P2的有效覆盖、P3的低成本列表/硬件遍历，收益才可能大。
[Raster I 的片上合成示例](https://github.com/raster-gpu/raster-i)和
[Arm Tile架构](https://developer.arm.com/community/arm-community-blogs/b/mobile-graphics-and-gaming-blog/posts/the-mali-gpu-an-abstract-machine-part-2---tile-based-rendering)
仅作思路，不能整套搬入Vitis/Vivado。

创新候选：**2D专用、保序且双缓冲感知的Tile后端**；无3D几何/深度/Shader。
需跨Tile裁剪与相交列表、防漏/重复Alpha、错误回退、BRAM映射、100MHz时序。
约15–25天，高风险。本月不与P1完整仲裁重构同时承诺，只作前两项不足后的升级备选。

### 共同的硬件安全条件，不单独包装成“再加QoS”

受限在途须先预留返回容量，测首数据/整事务/响应延迟，再决定授信和突发粒度。
现有水位QoS保持；AXI VALID在背压下必须稳定，B/ID/错误与完成标签正确。
借鉴 [AXI-RT](https://github.com/pulp-platform/axi_rt) 的预算/监测及
[LiteDRAM](https://github.com/enjoy-digital/litedram/blob/master/litedram/frontend/dma.py) 容量预约，不整库导入。
这为流水提供安全边界，本身不是保证提速的第五个魔法模块。

## 6. 功能创新：优先补赛题交互，再丰富外设

### F1：真实操控 + 录制输入后的公平性能回放（必选）

R7已有移动、HP/碰撞、擦弹和重开，只需替换自动驾驶输入层，不新写游戏引擎。
先复用Sapphire UART，接收短的按键状态包，非阻塞、有序号、坏包拒绝、
超时松键、每次处理数量上限。PC只转发键位，全部游戏状态仍由RISC-V更新。
板键修正后可支持横向躲弹；KEY0复位不可直接改成动作键。

实测候选和仓库peripheral XML的soc_gpio[0:1]都接GPIOR_27/_24；main读取
其低两位。官方手册“用户IO”表（PDF第34页、页脚33）KEY1/2为
GPIOR_22/P14、GPIOR_21/N14；前两个是LED管脚。不能把串口KEY提示当验收。

UART的RX/TX已映射GPIOL_02/R4、GPIOR_28/R14，3.3V；
官方BSP为115200、128 B FIFO。Type-C通过FT4232HL是USB设备侧桥，
**不是USB Host**。官方[UART API](https://www.efinixinc.com/docs-html/rv32-sapphire-ug/topics/riscv-sw-api-uart.html)
提供occupancy；不得在帧循环无条件调用等待数据的read。

6 B包×60次/秒时，128 B FIFO约356 ms满，接近CPU 2.8FPS一帧。
因此“GPU实时游玩 → 录一段输入 → CPU/GPU同段回放 → 恢复游玩”更稳妥，
CPU回放期间不接收新的实时输入流改变场景；确需CPU实时输入时再研究中断。
不能让两种模式各读不同的真人输入。

600 tick记录一字节键掩码约600 B，加已有初始状态、seed和资源版本即可；
测量前恢复相同逻辑，验证命令哈希和像素。创新表达为**交互轨迹驱动的可复现
异构基准**，不是宣称发明回放。UART接入约4–6天、回放约3–5天，软件线可
与GPU硬件线并行；修板键需2–4天及重新时序/板测。

校验：按住/松开、相反方向、掉线不粘键、超量坏包；重复轨迹同状态/命令；
实时GPU输入延迟与P95帧时间；CPU仍基础绘制。PC输入程序退出后板上继续运行。

### F2：低扰动性能驾驶舱与压力档位（必选）

复用现有计数和字形缓存，显示活动/目标数、完整帧时间、GPU绘制、
DDR读写、Cache字节、underflow增量、资源网络/后备状态。
游戏正常HUD不塞满诊断数字，另设诊断页；每30帧更新或按需采样。

深入事务探针可在测量模式启用，正式演示默认关闭。像之前逐命令探针会增加
512档约0.839ms，不能把“更多仪表”本身变成瓶颈。CPU/GPU最近有效数字仍在
主界面显示，标签明确；未测量不写60或0。约3–4天，主要是集成，不再加框架。

创新表达是把真实性能和异常变成观众看得懂的交互，而不是新画面素材。
验收屏幕与同一窗口串口一致、计数取差、溢出/无样本、开关前后观察开销。

### F3：场景资源缓存/预加载与断网可玩（推荐小范围）

继续使用现有GET/DATA与完整CRC；增加一个可切换的第二资源包、
“未就绪→下载→已校验→可用”状态以及可视加载进度/重试。
RISC-V决定何时预取，FPGA受控DMA写空闲资源区；仅校验成功且渲染不再引用
旧区时在帧边界切换，并失效纹理Cache及双缓冲恢复历史。

不是新增PC游戏服务，也不是承诺高速实时纹理流。9/26首轮1,036,800B资源
加载/校验约2391ms，约0.43MB/s；1Gbps链路速率不代表当前停等协议吞吐。
第一版预加载放在菜单/场景切换空隙，连续渲染背景下载是额外总线QoS挑战，
先不要抢GPU帧预算。

约5–7天，先完成现有素材加载→拔网线继续→恢复→切换包的证据。
跨包地址规划/生命周期要先冻结，避免错误资源覆盖和历史失效遗漏。
既有CRC重试不能再包装成新功能，创新候选是CPU主导的资源生命周期与帧边界提交。

### F4：USB手柄、SD和声音（选做，最多一个）

| 选项 | 可复用来源 | 真实资源边界和风险 |
|---|---|---|
| USB HID手柄/键盘 | [usb_hid_host](https://github.com/nand2mario/usb_hid_host)，Apache-2.0；[外接Host板](https://github.com/nand2mario/usb_host_pmod) | 当前Type-C不能转Host，需外接USB-A/VBUS及电气适配、时钟/IO/ROM移植；参考核主要低速，不承诺任意现代手柄；约10–15天，零件到位后才计 |

| 音效/蜂鸣反馈 | 需先确认外接器件及驱动 | 当前HDMI是DVI编码路径，不能从有HDMI口推断已有音频；没有已验证板载codec链路。低风险蜂鸣仍需器件/限流/驱动，完整HDMI音频本月不推荐 |

Ti60F225A_V4_SCH.pdf；候选peri.xml与板顶层/adapter；源码BSP和官方文档。
J7为QSE接口，不是现成PMOD；候选HVIO未占用不等于已完成电气/球号检查。
没有外设硬件清单前，不把SD/USB/音频列为必交付。

## 7. 不推荐的路线与止损条件

- **继续扩大前景Cache：**3104B图集已被4KiB覆盖，背景不命中，不是现在主要杠杆。
- **整背景BRAM缓存：**ROI为898560B，约878KiB；[Ti60](https://www.efinixinc.com/shop/ti60.php)
  全部256个RAM10原始总量约320KiB，还要扣已有145个资源估计。根本放不下；
  小Tile/FIFO可行，但PnR映射和端口效率仍需测。
- **加更多乘法器：**Alpha事务已改善，缺乏当前DSP饱和证据；目标不对应最大开销。
- **直接超频或换官方CPU：**最新100MHz setup/hold余量+0.871/+0.026ns，
  不是整板超频许可；CPU基线冻结。GPU独立时钟还引入CDC/时序集成，本月优先低风险结构效率。
- **全扫描线Sprite合成：**原背景可在显示时合成省Copy，但要替换输出路径，
  坏行可能超过时限。按两条1080p线约29.63us、100MHz约2963周期，
  最坏512个8像素Sprite就4096采样，单像素/拍无法保证；Alpha/背景尚未计。
  还要保留赛题BitBlt显存证据，不适合作为本月主线。
- **整库换GPU/DDR/CPU、同时上SD+USB+HDMI音频：**时间和验证面不匹配。
- **只讲面积/理论带宽收益：**P2初步结果已证明低字节不一定低成本。
- **以Hash相等跳过工作当像素严格相等：**默认采用确定性覆盖和必要全恢复，
  不让CRC碰撞概率成为正确性依据。

止损：任何架构在第14天仍不能通过像素/反压/错误边界，回退至可封版的V2
候选和较小优化；若降低平均但增加最大帧/下溢，则不纳入正式演示。
保留全Copy、老APB命令和原CPU对照，方便定位与通用赛题测试。

## 8. 推荐组合、一个月里程碑与选择门槛

**主推荐：P1连续Copy/受限流水 + P2成本感知恢复；软件并行F1/F2，
F3只做可验收的小范围。**P3作为高档位前端余量不足时的替代大项，
P4只做受限研究，不把四个硬件革新全部承诺。

| 天数 | GPU性能线 | 功能/验收线 | 输出和决策 |
|---|---|---|---|
| 1–3 | 基于已有分段结果，补事务级等待/响应/FIFO波形；保留同入口基线 | 核对并冻结输入/回放合同，UART非阻塞接入；查冷启动与热重载差异 | 明确Copy时间中延迟/耦合占比，不重复跑长期大阶段 |
| 4–7 | P1连续Copy子集；P2先用现有Copy比较16/4、32/4与全恢复 | GPU实时输入、松键/坏包/断连；修板键外围映射 | 同像素、同普通固件量化净收益，选择一条主要大架构 |
| 8–14 | 如果搬运仍主导，受限读写流水；若前端更主导，改选P3，不双线展开 | 输入录制与CPU/GPU同段回放、低扰动HUD | 第14天必须有可工作的候选，不能只有接口占位 |
| 15–21 | 配置P2代价/全Copy回退；测最大帧和更高对象档位 | F3单包切换/断网持续、交互流程与错误恢复 | 以真实可见数给60FPS稳定档位；高档失败边界也保存 |
| 22–25 | 同版整体回归、像素/硬件错误/下溢、冷启动/重载定位 | 实际输入、断网/服务器退出、至少30分钟耐久 | 不再增加大模块；未解异常决定发布限制，不隐去 |
| 26–30 | 冻结正式位流/固件/资源及hash、复现命令 | 演示/答辩素材，预留修复时间 | 完整版本清单、性能曲线、来源/许可、已知限制 |

工期为风险估计，团队并行时不能把表中单项工期全部相加或都视为必做。
硬件由负责人主导，组员保持软件输入/资源/展示独立；共用格式先定合同和独立
向量，避免“硬件等软件产物、软件又等硬件实现”的循环依赖。
详细逐文件计划待选择门槛通过后再写，现有本地后期计划不被本报告擅自替换。

发布验收必须同时看：

1. 最终像素等价、Alpha/Key顺序和同场景CPU基线；硬件错误为0。
2. 真实完整帧、P95/最大帧、300连续GPU帧、下溢为0，报告目标/可见Sprite区间；
   P5≥60本身不等于每帧60，若称稳定60还需无错过显示deadline。
3. 实际人机输入及同段回放；CPU数字真实，GPU/CPU时窗与场景一致。
4. 网络CRC/回退状态、断网继续、输入掉线、冷启动/复位/热重载、30分钟耐久。
5. 同一BIT/固件/资源/server的哈希与来源记录；局部通过不冒充全项目通过。

最终值得答辩的故事不是“又接了一个IP”，而是：
**RISC-V保留控制职责，通过可复现互动工作负载，选择显示安全、保序且碎片
感知的搬运/命令架构，把优化收益落实到真实帧预算。**
