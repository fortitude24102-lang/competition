# 游戏难度菜单与网页同步设计

日期2026-10-08；代码基点e97b2dc9b18b7b1e2b5be745024ba8be2a7a2a4a。状态：用户已确认交互方案，本书面设计待审阅；功能尚未实现，不是上板记录。沿用现有项目docs目录，不替换V3两周计划及其未完成验收。

## 1 已确认的结果与不变边界

开机进入难度菜单，HDMI和网页均展示四项。网页选档后Sapphire初始化对应游戏，键盘仍控制显示屏上的飞机。玩家死亡后立即结束该局并回到菜单，不再自动续局。网页“一键重选难度”结束当前局、返回菜单；R仍重开当前难度，菜单内R不自动开始游戏。

| 等级 | 请求活动对象档位 | HDMI标签 |
| --- | ---: | --- |
| 难度一 | 64 | LEVEL 1 - 64 SPRITES |
| 难度二 | 128 | LEVEL 2 - 128 SPRITES |
| 难度三 | 256 | LEVEL 3 - 256 SPRITES |
| 难度四 | 512 | LEVEL 4 - 512 SPRITES |

请求档位不是每帧实际可见数。射击槽、离屏、Key及Alpha工作量均保持现有定义，不删除元素来假称达档。512档历史R7实测约30FPS，不能标成稳定60；新菜单交互版的各档成绩必须重新标明测量场景。

PC只提供资源、输入桥接和板端信息展示，不决定飞机位置、死亡、碰撞、弹幕或绘图命令。官方Sapphire、GPU100MHz、原GPU ABI/RTL后端、960×540 RGB565和1080p60 HDMI、vblank双缓冲保持。原基础CPU渲染不优化、不人为降速；保留C比较回放及最近有效CPU/GPU成绩。GPU寄存器差分、Copy/实例等未采用候选不因本功能被重新启用。

## 2 方案选择

采用现有管理UDP8090的明确游戏命令，复用32字节包、会话、CRC、序号、单网页所有权和现有收发缓存。软件与control_udp_rx的合法包检查一起扩展；不改资源UDP8080或Asset DMA。

不以模拟方向键组合表达选档：组合键与飞机输入混用容易产生残留或丢失操作。也不新增独立游戏服务器/FPGA HTTP栈：现有本机HTTP8765和管理通道已能承载请求。浏览器继续使用原生HTML/CSS/JS、Python标准库网关，无新增依赖。

## 3 板端状态与操作顺序

增加与既有LIVE/CPU/GPU渲染模式正交的MENU/PLAY状态。v3_runtime保存当前等级、菜单原因和等待零键标志；游戏大对象继续放既有私有DDR区，不能在4KiB栈增加副本。

- 初始化：MENU，无游戏逻辑推进；保留已加载背景、图集、字体和竞赛图片。
- START(level)：仅MENU允许，等级必须1～4；重新初始化游戏/录制/时钟为固定seed7和当前资源epoch，设置PLAY，清除本局计时与未完成比较。等级映射由Sapphire表决定。
- LIVE死亡：任一逻辑tick使HP=0后立刻停止本次追赶循环并转MENU。不再调用后续死亡倒计时/自动重生。冻结R7/bullet_step原函数保持，用交互runtime隔离新行为。
- MENU命令：在PLAY、MENU或比较回放中均可执行；中止本局/回放、清除待执行动作，回MENU。已完成CPU结果可保留但标过期；未完成窗口不得发布为新成绩。
- R：PLAY/LIVE下重开相同等级，重新录制及清理本局统计；MENU忽略。比较回放期间不改变录制输入，沿用原R忽略行为；“一键重选难度”作为独立管理命令仍可中止回放。
- C：PLAY/LIVE保留原录制比较入口，MENU忽略。录制未满600tick时显示等待有效回放，不伪造CPU成绩。CPU/GPU录制重放期间不因录制内HP变化跳到菜单或受真人方向键影响；返回LIVE后再按实际游玩状态处理死亡。

START、MENU、R发生时清除pending_pressed/pending_released、游戏时钟积累和浏览器已记录的按键。不能把input_update的会话/已消费动作序号清零来制造新的R/C事件。进入新局后仅在收到更新的有效零键快照后重新接纳飞行输入，旧包和持续旧按键不能控制新局。

失焦、租约超时、断连依旧清键，不自动选择难度或重开。断网时板端已有游戏按零键继续，死亡仍能自行回菜单；网页显示失联，不虚构同步成功。

## 4 兼容管理包扩展

原AGC1 version1、32字节大端头、session/sequence及CRC32不改。原HELLO=1、KEYS=2、ACK=3以及KEYS掩码0xff和第三数据字为0的合同不变；未知type、越界或非法保留值仍拒绝。

新增type4 GAME：16～19字节opcode、20～23字节level、24～27字节request_id。opcode1=START且level1～4；opcode2=MENU且level0。request_id为非零u32，按模2^32新旧规则比较，与R/C的action_sequence独立。控制session必须已通过HELLO，包年龄≤250ms、线序号新、来源会话匹配。RTL先检查长度/CRC/合法opcode和level；软件仍复核全部字段及会话。

GAME属于同一全局控制线序号流，与KEYS共同排序。合法接收时只更新会话租约/线序号并把held keys清零，保留已消费的R/C动作序号；不能将GAME的数据字解释为方向或action_sequence。runtime执行一次的request_id去重与网络线序号的新旧检查是两层不同保护。

新增type5 GAME_ACK，仅板端发送：数据字为request_id、result、snapshot_floor。result0=已完成状态切换，1=当前状态不允许（例如PLAY中直接START），2=执行失败。包session为当前控制session，sequence回显被确认GAME包的线序号。result0必须在runtime完成重置/清键后才产生，不可把“接收到了”当“已执行”。ACK的发送复用原32/128字节TX描述符。

同一session仅一个未完成GAME请求；同request_id/同payload的重试不再次初始化，重发已保存结果；相同id而不同payload拒绝。较旧id不能再次应用。待执行槽忙时新请求排空丢弃并计数，由网关有界重试；不扩大队列。保存本会话最近已处理请求及结果即可，不保存无界历史。session失效/切换时取消未执行请求及待发游戏ACK，不能将旧请求带入新会话。

HELLO ACK最高优先，GAME_ACK其次，遥测最后；所有提交非阻塞，慢PC不阻塞渲染。一次处理不超过既有4包预算，不增加MAC FIFO容量。

snapshot_floor在状态切换时记录nc_device全局snapshot_id上界，包含已构造的旧遥测。网关仅接受序号严格新于该上界的后续快照来确认新场景，防止迟到旧快照把菜单/成绩回滚；完整128字节原子快照和现有全局排序规则保留。迟到旧ACK不能确认另一请求或另一session。

切换时丢弃尚未序列化的旧pending_telemetry，并在新状态重新构造；已经进入MAC的旧整包不能中途覆盖，其snapshot_id必须不超过floor。否则旧pending在切换后获得新序号，会绕过上述门槛。R重开和本机死亡返回MENU也清除旧pending和统计窗口，保持snapshot_id全局递增。

## 5 网关与网页合同

保留原/api/control和键盘心跳；新增同源POST /api/game，JSON恰含token、client、opcode、level、request_id。token/Origin/Host/Content-Length、1024字节上限及类型校验沿用原安全策略。opcode字符串仅start/menu，level仅对应合法值。需同一已拥有控制的client和新鲜真实板端能力快照；无所有权返回409，无有效板端能力/ACK返回503，参数错误400。HTTP接受只表示进入有界待确认槽，返回202，不直接宣称游戏已开始。

点击难度可触发既有零键获取控制流程；收到真实HELLO ACK和菜单能力后才能提交GAME。其他网页已拥有控制时显示冲突，不能抢占。按钮执行时清除KeyboardState并发送零键，等待板端执行结果及新于snapshot_floor的快照；期间禁用重复点击。网页仍维持有界零键心跳以免等待ACK时租约过期。

网关最多保存一个待确认请求，每50ms最多重发一次相同request_id（线sequence更新），最长2s；连同HELLO/KEYS仍满足总60包/秒上限，保留键盘租约心跳的发送机会。ACK失败、超时、失焦/关闭、所有权释放或固件会话重建即取消待确认请求，不自动跨会话重放。重复同HTTP请求返回同一处理中/结果，不再排第二个操作；另一新请求在pending期间409。执行结果和板端新快照经现有status/SSE展示，超时提示状态未知并以随后真实遥测恢复，不能假定未执行而盲目再重开。

保留AGT1的27数据字/128字节、现有有效位及字段含义。status_flags新增bit10=MENU、bit11=GAME_MENU_CAPABLE，允许掩码更新为0x007f0fff；MENU同时置既有PAUSED。PLAY等级由requested_sprites的64/128/256/512映射；MENU没有活动游戏，requested/visible/Alpha/Key游戏计数均为0，不能把菜单字形算Sprite。无bit11的旧固件仍可显示原遥测和使用原键盘，新菜单按钮明确标不支持，不主动发送新命令。

反向兼容边界：旧网关的严格status掩码会拒绝新能力位，因此新固件必须和升级后的网关/网页配套使用，不称旧网关可完整使用新固件。升级网关仍可识别旧固件，并保留其基础输入/遥测。部署保存旧服务启动参数及程序版本供整体回退。

网页菜单中文四卡片，显示等级及请求数；PLAY显示当前难度、一键重选和原性能面板。重选不是重启FPGA、烧录或重启PC服务。板端死亡时网页只根据新鲜MENU标志回到选择界面，不自行推算HP/碰撞。失联或快照≥500ms过期时保留最后状态并标过期，禁止据旧快照开始新局。

## 6 HDMI与渲染开销

逻辑960×540中保留原顶部960×72性能/标识区；菜单主体四卡片放x96/y144、x496/y144、x96/y288、x496/y288，各368×104，均不重叠、不越界。标题和提示使用既有英文大写/数字字形，网页用中文；不追加中文字库/图片字体资源。竞赛图片沿用原位置，不因菜单迁入覆盖性能文字。

使用既有Fill/Copy、字体atlas和overlay scratch绘制菜单。进入MENU时两个显示buffer分别标脏，各自完成菜单绘制后再于vblank可见。静止菜单不每帧构建字形或做全屏背景Copy；只在菜单内容/连接状态变化时更新受影响区域，交换已完整绘制的缓冲。持续按现有帧节奏轮询管理、发布5Hz遥测，不能用长时间等待按键阻塞网络。

进入PLAY时按原完整背景恢复路径绘制首帧，不能留下菜单残影；任何切换/初始化错误使缓存无效、报告错误，不提交半绘制场景。GPU完成和PRESENT仍遵守旧tag/双缓冲规则。只有实际游戏帧计入FPS窗口，MENU等待/字体重建不得变成GPU游戏成绩；切换档位重置GPU窗口和P95，CPU旧成绩明确过期，不能混合不同难度或未完成回放。

具体有效性：MENU的游戏GPU时序有效位清零，性能位置标上局/过期或不可用，不报告菜单FPS；START清除CPU有效位及CPU FPS，直到本局完成基础CPU回放才重新有效，避免跨档借用成绩。R同档重开可以保留上次完整CPU成绩但置过期；中止回放仅丢未完成窗口，不改已完成成绩或测量公式。

## 7 拟触及文件与验收边界

协议：include/v3_control_protocol.h、net_control.h与src/net_control.c；RTL仅自有rtl/net/control_udp_rx.v必要合法包判定，保持一文件一模块，vendor不动。
板端：v3_runtime.h/c、v3_demo.c及必要的菜单绘制小模块game_menu.h/c，复用原字体/命令缓冲，不重写游戏引擎；构建源清单同步新模块。冻结R7及基础CPU绘图不改。
PC：tools/control_gateway/protocol.py、gateway.py、web/index.html/dashboard.js/styles.css；沿用原静态文件白名单、快照有效性、CSV和有界HTTP/UDP线程。
检查：受影响C、Python、JavaScript和control_udp_rx/SoC网络胶合原有入口，新增失败先行检查，不新建测试框架。

必须验证：四等级映射及1/4/越界；启动MENU；START后正确PLAY；死亡当tick返回MENU且不自动重生；R同档重开；任意模式MENU；重复/乱序/旧session/旧按键/租约超时；ACK丢失有界重试而不重复初始化；新旧协议能力门控；600tick公平回放与中止不发布部分CPU结果；两缓冲无菜单残影；旧GPU字段/Alpha/Key顺序和冻结R7未变。

先离线真实驱动/逻辑/网关检查及RTL定向仿真，再验证独立固件RAM+4KiB栈静态容量，只有拟改网络RTL才生成隔离候选位流并检查100MHz时序/资源/CDC。沿用当前已合格旧GPU后端，不能覆盖原BIT、正式release或官方Demo。

原V3_PROBE_FRAMES性能诊断可以明确从指定档位直接PLAY，但只能在独立诊断构建中使用；正常交互构建仍必须启动MENU。保留冻结R7诊断入口，不把菜单等待混进旧性能基线，不以试验开关改变正常产品的四档语义。

板端可用时仅JTAG加载合格候选，验证两端菜单、四档、实际飞机输入、死亡/重选、断网/重连及下溢/错误；每档数字报告完整工作量和实测窗口，不拿菜单60Hz当512游戏60FPS。现有诊断预热下溢缺口须在用于新候选验收前补齐。显示外观需用户观察确认，不能用传输CRC代替可见画面证明。失败时恢复原合格BIT/BIN和服务配置，不写Flash。

本功能不代替V3完整同版性能消融、30分钟耐久、512@60/1024目标或历史SoftwareDriverSpec/PangoBringupSpec问题。文档/源码本地提交与远程推送区分，本次没有main推送授权。
