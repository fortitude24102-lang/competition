# R7 分段测量：命令构建、提交压力、GPU 执行与背景 Copy

日期：2026-09-30。基线源码 `8d1b395`。本轮是诊断，不是新的性能发布或优化收益证明。

## 边界与口径

- 复用官方 Sapphire、100 MHz GPU/CLINT、960×540 RGB565 双缓冲、1080p HDMI、4 KiB 纹理 Cache、R7 同一状态序列及 HUD 字形局部更新。CPU 对照、画面算法、对象/Alpha/Key 数量、RTL、主频、Flash、`release/v2/` 均未修改。
- 使用测试入口 `sw/efinix_gpu/tests/test_board_render_phases.c`，直接包含普通 main 的状态与辅助函数；测试专用 `submit_probe.h` 包含原驱动，正常发行版不包含此头文件。
- 64/256/512 档各测探针关闭、开启两组；每组 30 帧预热 + 300 连续 GPU 帧，游戏状态重置为同一 seed=7。CPU 数字在此终端诊断中不测量，普通对比固件保持原样。
- `build_us` 为构建场景命令 + 背景 HUD 裁剪；`submit_us` 为各次 gpu_submit 内部计时之和，包含校验、寄存器读写和队列压力；`blocked_us` 是首次 AGAIN 后到该调用退出的重试区间，**包括 refresh、重复校验/读状态和最后一次提交，不是纯 APB 等待**。`nonblocked_us=submit_us-blocked_us` 同样不能称为纯寄存器写入耗时。
- `tail_us` 为最后 tag 等待。`scene_us` 包含整批提交、最后等待及场景后同步；逐命令计时、调用/循环等额外开销不完全落在 submit/tail 内。
- `busy_us` 来自硬件 active 周期，active 为引擎 busy，包含队列/内存等待；它与 CPU 提交和队列阻塞**并行重叠**，不能相加。`stall_us` 仅统计已有 AXI VALID&&!READY 或像素握手背压，不含所有 DDR 响应延迟，也无法区分仲裁、DDR 控制器及读写耦合。
- `work_us` 从上一 PRESENT 返回到本帧 PRESENT 调用，含上一帧统计/游戏更新和本帧所有工作。每帧 hardware snapshot 会产生额外观察开销；`step_us` 单独测游戏更新，和 work 是包含关系，不重复加。日志只在整组结束输出。
- 隔离测试按 BACKGROUND → SPRITES_ORDERED → PRESENT，原命令顺序不变，不按 opcode 重排；中间等待/读计数会破坏原流水重叠，不能把隔离结果直接相加当成正式帧率。

探针开关前后 FPS 档位未变，读写/Cache 工作量一致。但不能称其开销可忽略，不能拿开启探针的时间替代发行固件成绩。关闭探针时 submit/blocked/tail 输出 0 表示**未测量**，不表示没有开销。

大量 queue-pressure 时间不代表 APB 本身慢：背景 Copy 执行期间，16 深队列与软件 outstanding 窗口会饱和，CPU 正在等待 GPU 消化任务。当前已批量入队，只在批尾等待；“去掉每命令完成等待”并不是尚待实现的优化。

关闭探针仍保留分段计时、计数快照和测试入口，链接布局也与普通固件不同。本轮 512 场景 13.436 ms 与上轮五档普通入口诊断 11.200 ms 不能直接作同二进制性能退化比较；先在同一测量入口比较开关，然后最终回归普通固件。256 本次 300 帧均符合节拍，也不推翻上轮平均 59.7 FPS 的历史记录，不作为新的长期稳定性承诺。

## 背景与 Sprite 隔离

512 档的 tick=0/90/180：

| 阶段 | 墙钟时间 | GPU busy | 背压 | 提交总计 | 队列压力 | 最后等待 |
|---|---|---|---|---|---|---|
| 背景 Copy | 7.589–7.626 ms | 7.553–7.603 ms | 4.583–4.630 ms | 0.021–0.034 ms | 0 | 7.522–7.567 ms |
| 原顺序 Sprite | 6.338–6.483 ms | 4.426–4.445 ms | 2.429–2.447 ms | 4.457–4.657 ms | 0.672–0.978 ms | 0.014–0.047 ms |

背景每次精确读取、写入各 **898,560 B**（960×468×2），Cache 命中 0；合计搬运约 1.797 MB，实测聚合读写吞吐约 236 MB/s。这是 GPU 的读写合计吞吐，**不是 DDR 芯片总带宽或网络带宽**。Sprite 的 Cache 命中约 86–87 KB，背景 DDR 读取占连续场景读流量约 97.7%，背景写入占约 94.5%。64/256 档背景隔离范围约 6.865–7.624 ms，反映显示节拍/仲裁条件影响，不代表同一场景像素发生变化。

## 决策：下一项优先背景 Copy 通路，随后有序命令前端

事实：背景是最大的单项 GPU 硬件时间，512 隔离背景 busy 的约 60% 周期计入握手背压；HUD 字形更新只有约 0.25 ms，进一步增加文字 DMA 不是首选。

代码检查：现有 Copy 已有 32 位字直通、INCR burst、4 KiB 切分；AxiRead/WriteEngine 已能产生最长 256 beat，不能将“首次引入突发”当成本轮创新。Copy 仍逐行发请求，等该行读/写结束后才推进；写引擎每个 burst 等 B 再发下个 AW；源数据直连写通路，而 DDR 仲裁虽已有 256-beat 响应队列，读通道仍一次只处理一个事务。**目前无法仅凭总背压计数判断其中哪一个是主因，需要定向波形/事务测量。**

建议的最小次序：先检查连续 Copy 的行边界/突发间隙，再评估源读与写回解耦及受限在途请求；已有 FIFO/QoS 能复用就复用，不立即引入第二套 DDR 控制器或大缓存。开源参考为 [verilog-axi 的 AXI CDMA/FIFO](https://github.com/alexforencich/verilog-axi)；该仓库已由 [Taxi](https://github.com/fpganinja/taxi) 接替维护，真正复制代码前需核对对应版本许可。现有显示水位保护保留，不靠停显示或禁用 QoS 得分。

第二顺位：按 [Endeavour2 的批量图形 DMA](https://github.com/petrmikheev/endeavour2) 思路评估小 Sprite 状态模板/有序实例流，降低 512 档 3.1 ms 构建和重复提交负担；PC 仍只存资源、RISC-V 仍决定游戏与命令。Alpha/重叠绘制不全局重排。批量、DMA 本身不是原创，创新候选是针对小 Sprite 工作负载的紧凑描述与显示余量约束下的搬运调度，收益尚待证明。

本轮未实施上述架构修改；测量已完成，后续变更先选定定向设计，再用像素等价、真实刷新、零下溢和普通固件同场景比较验收。
