# RV32I 五级流水线 Chisel CPU 设计

日期：2026-08-27

## 1. 目标

在现有 Chisel 工程中实现一个 RV32I、ILP32、五级单发射 CPU，用于当前 SoC/加速器 Demo。设计优先保证：

- 正常算术指令在流水线填满后达到每拍提交一条指令；
- 每级组合路径最多包含一次主要 32 位运算，避免跨级 ready 长链；
- CPU 核与存储器、AXI、缓存和外设解耦；
- 保留加入 M 扩展、CSR/中断、分支预测和缓存的清晰边界；
- 日常开发只依赖 Chisel 测试，Vivado 仅用于里程碑时序检查。

首版不实现 RV32M、压缩指令、原子指令、浮点、CSR、特权态、中断、MMU、缓存、动态分支预测和双发射。

## 2. 参考代码边界

原始 LoongArch CPU 工程仅作为只读参考，不在原目录中修改、生成或删除文件。后续参考以下本项目快照：

- `references/loongarch-core-v2/core_v2/`
- `references/loongarch-core-v2/integration/`

可借鉴 `core_v2` 的取指/访存握手、单发射控制、提交跟踪和顶层适配边界。LoongArch 译码、立即数、CSR、异常编码和系统指令逻辑不复用。

## 3. 指令集与工具链

首版实现 RV32I，ABI 为 ILP32。裸机程序使用 GNU RISC-V 工具链，主要编译参数为：

```text
-march=rv32i -mabi=ilp32 -ffreestanding -nostdlib
```

工具链和相关环境文件安装在 `D:\Chisel-environment\riscv-toolchain`，项目脚本通过该固定位置调用；可将其 `bin` 目录加入系统 PATH，但不把工具链复制进项目仓库。

覆盖整数运算、逻辑、移位、比较、条件分支、`JAL/JALR`、加载、存储、`LUI/AUIPC`。`FENCE` 作为不改变体系结构状态的 NOP。`ECALL`、`EBREAK` 和非法指令产生 trap 事件。

## 4. 流水线结构

流水线固定为 IF、ID、EX、MEM、WB 五级，使用四组带 `valid` 位的显式流水寄存器。内部不串接通用 Decoupled 流水级，以免形成从 WB 到 IF 的组合 ready 链。

### IF：取指

- 保存和更新 PC；
- 并行计算 `PC + 4`；
- 处理 EX 级分支/跳转重定向；
- 通过深度为 2 的 Chisel `Queue` 缓冲取指响应；
- 重定向时清空错误路径队列；若旧 PC 的请求已经握手但尚未响应，使用一个 `dropResponse` 状态丢弃该次响应，再从重定向 PC 继续取指。

### ID：译码

- 生成 RV32I 控制信号和立即数；
- 读取双端口寄存器堆；
- 检测立即可知的非法编码；
- 将操作数、寄存器编号和紧凑控制信息写入 ID/EX。

ID 级不执行 32 位算术，避免“译码 + 操作数选择 + ALU”落在同一路径。

### EX：执行

- 进行 EX/MEM 和 MEM/WB 两级旁路比较与操作数选择；
- 普通数据通路只经过旁路选择和一次主要 ALU 运算；
- 分支比较器、分支目标加法器与普通 ALU 并行；
- 计算加载/存储有效地址；
- 生成跳转重定向、访存信息和写回候选值。

### MEM：访存

- 发出已在 EX 级计算好的地址；
- 生成或使用已寄存的字节使能和写数据；
- 等待数据端口响应，等待期间冻结相关流水状态；
- 完成加载字节/半字选择及符号或零扩展后写入 MEM/WB。

MEM 级不重新执行地址加法。

### WB：写回与提交

- 在 ALU、加载数据和 `PC + 4` 中选择最终结果；
- 写回寄存器堆，禁止写入 `x0`；
- 输出按程序顺序的 commit 跟踪信息。

## 5. 组件边界

- `Rv32Core`：连接流水级、存储器端口、trap 和 commit 接口；
- `Frontend`：PC、取指请求、两项取指队列和重定向；
- `Decoder`：RV32I 译码与立即数生成；
- `RegFile`：32×32 位、双读单写、`x0` 恒零；
- `Execute`：ALU、比较和分支目标计算；
- `PipelineControl`：旁路、load-use 暂停、访存等待、冲刷和优先级；
- `LoadStoreUnit`：对齐检查、写掩码、加载扩展和数据请求格式；
- `CoreBus` 数据结构：定义与实现无关的取指/数据请求响应。

这些是按职责划分的具体模块，不建立插件框架或单实现抽象层。

## 6. 存储器接口

指令端口和数据端口相互独立，均采用 ready/valid 请求响应接口，每个端口首版最多允许一个未完成请求。

请求至少包含地址；数据请求另外包含读写方向、访问宽度、写数据和 4 位字节掩码。响应包含 32 位读数据和错误标志。包括 store 在内的每个已接受请求都必须返回一次响应，以便精确报告总线错误。

CPU 核不包含 SoC 地址译码或 AXI 信号。RAM、UART、加速器寄存器、缓存和 AXI 适配器均位于核外，避免外部互连逻辑进入 CPU 关键路径。

## 7. 流水控制

控制优先级从高到低为：reset、trap、分支/跳转重定向、数据端口等待、load-use 冲突、正常推进。

当不同流水级同拍报告事件时，以程序顺序最老的有效指令为准：先阻止更年轻指令产生写回或存储副作用，再冲刷其后的流水级。这样保证 trap 精确，且不会因年轻分支重定向覆盖老指令的访存错误。

- EX/MEM 和 MEM/WB 结果旁路到 EX；
- 若加载结果尚未产生且下一条指令依赖它，插入一个气泡；
- 数据响应延迟超过一拍时，保持相关流水寄存器不变；
- 分支在 EX 级解决，静态预测不跳转；跳转或实际跳转的分支冲刷 IF/ID 和 ID/EX；
- store 数据依赖使用同一旁路规则，不额外等待已可用的 ALU 结果；
- commit 只在 WB 有效且指令没有 trap 时产生。

无存储器等待时，独立 ALU 指令稳态 IPC 为 1。首版不承诺固定 MHz，实际频率以里程碑综合结果为准。

## 8. Trap 与错误处理

首版检测：

- 非法指令；
- `ECALL` 和 `EBREAK`；
- 未按 4 字节对齐的取指或已采用的分支目标；
- 未对齐的半字/字加载和存储；
- 指令或数据总线错误。

异常指令不写寄存器、不发出无效存储，也不产生正常 commit。CPU 输出 `trapValid`、原因、异常 PC 和指令，然后进入 halt 状态直至 reset。此行为适合裸机 Demo 和测试结束标记。

以后加入机器态时，独立 System 单元接收同一 trap 信息，保存 `mepc/mcause` 并重定向到 `mtvec`；普通流水线和外部存储器接口无需重写。

## 9. 时序约束原则

- 每一级最多包含一次主要 32 位加法、移位或比较运算；
- 分支目标加法与普通 ALU 并行，不通过共享 ALU 串联选择器；
- 地址译码和 AXI 适配不进入 CPU 核；
- internal stall/flush 使用集中控制，不传播跨五级组合 ready；
- 高扇出控制在流水级边界寄存，必要时由综合工具复制；
- 后续乘除使用多周期握手或独立流水单元，不加长普通 ALU 路径。

Vivado 仅在三个里程碑执行：五级流水线首次贯通、完整 RV32I 测试通过、SoC 最终集成。每次记录最差路径、逻辑级数和裕量，再决定是否调整流水边界。

## 10. 验证策略

快速循环使用 Chisel 测试：

1. 单元测试译码、立即数、ALU、分支、寄存器堆和 LSU 格式；
2. 流水线定向测试旁路、load-use、连续跳转、冲刷、总线等待和 trap 精确性；
3. 使用 GNU 工具链生成 RV32I 裸机程序，检查内存签名和 commit 顺序；
4. 在指令集里程碑运行固定版本的上游 RISC-V `rv32ui` 兼容性测试；
5. 生成 Verilog 后执行编译检查，但不手工编辑生成文件；
6. 仅在三个里程碑运行 Vivado 综合和时序报告。

每个新增功能先加入一个能在错误实现下失败的最小测试，再写 Chisel 实现。

## 11. 后续扩展顺序

扩展按实际需求加入，不预先实现空框架：

1. RV32M 多周期或流水乘除单元；
2. Zicsr、机器态 trap 和中断；
3. 简单 BTB/BHT；
4. 指令缓存和数据缓存；
5. 需要更高吞吐时再评估更深流水或双发射。

上述扩展不得改变现有 commit 接口和核外存储器请求响应语义。
